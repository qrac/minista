# v4.0.8とv5の性能比較（2026-08-14）

## 結論

- 同一のv5 docsソースによるclean buildは、v5がv4.0.8より28.7%高速だった。
- 16個のplaygroundのclean buildは、中央値で43.7%高速だった。Image以外の15個はすべて38.2〜45.8%高速だった。
- docsのcold devは、起動から最初のレスポンス完了までv5が2.7%遅かった。一方、直後の同一ページへのレスポンスは83.5%短縮され、約6倍高速だった。
- Image playgroundだけはclean buildで8.0%、キャッシュ済みbuildでも10.4%遅かった。今後追跡する性能課題とする。
- 測定中、v5のSearchが`pre`内のコードを索引化する回帰を検出した。除外処理を修正すると、docsの検索JSONは763.60 KBから63.41 KBになり、v4.0.8と同一の内容およびハッシュになった。以下のSearch結果は修正後の値である。

## 比較対象

| 項目 | v4.0.8 | v5 |
| --- | --- | --- |
| branch | `main` | `v5` |
| commit | `4e06452e5b2b536998c54d7f91a92e10e426eff2` | `8752270a7b165e5bd62c8f0f71217bdc91374b5e` |
| package version | 4.0.8 | 4.0.8 |
| Node.js | v26.2.0 | v26.2.0 |
| Vite | 8.2.1 | 8.2.1 |
| React | 19.2.8 | 19.2.8 |

Apple Siliconホスト上でNode.jsをdarwin-x64として実行した。各branchを`git archive`で`/tmp`の別ディレクトリへ展開し、それぞれのlockfileから`npm ci`した。依存関係のinstall時間は測定に含めていない。

## 測定方法

- buildは対象の`dist`、`.minista`、`node_modules/.minista`、Vite cacheを削除するclean buildとした。
- docsはwarmupを1回行った後、branchの実行順を交互に変えて5回測定し、中央値を採用した。
- playgroundはwarmupを1回行った後、同様に3回測定し、中央値を採用した。
- devはサーバー起動から`/docs/`の最初のレスポンス完了までと、直後の同一URLへのレスポンスを測定した。
- docsのbranch固有ソース比較に加え、v5の`docs/src`を一時的にmain環境へ複製した同一ソース比較も行った。リポジトリのmainは変更していない。
- Imageのキャッシュ済み測定だけは、最初のbuild後に画像cacheを保持し、`dist`のみ削除して3回測定した。

## docs

単位はms。変化率の負値はv5の短縮を表す。

| 条件 | v4.0.8 | v5 | 変化率 |
| --- | ---: | ---: | ---: |
| branch固有ソース: clean build | 8,326.1 | 6,111.3 | -26.6% |
| 同一v5ソース: clean build | 8,533.2 | 6,082.9 | -28.7% |
| branch固有ソース: cold dev + first response | 6,124.9 | 6,548.8 | +6.9% |
| 同一v5ソース: cold dev + first response | 6,117.8 | 6,285.5 | +2.7% |
| 同一v5ソース: first response部分 | 4,538.9 | 4,791.8 | +5.6% |
| 同一v5ソース: cached response | 260.0 | 43.0 | -83.5% |

同一ソースの出力サイズはv4.0.8が1,258,566 bytes、v5が1,258,528 bytesで、Search修正後は実質的に同等だった。cold devの初回処理にはProject Graphやsessionの初期構築が含まれるため、v5では小幅な増加が残る。2回目以降は長寿命sessionとページcacheの効果が明確に現れている。

16個の中央値合計は39,527.7 msから24,597.0 msへ37.8%短縮された。Imageを除く小規模fixtureでは、v4.0.8にある追加のCLI/Vite process起動コストをv5の単一lifecycleが削減した効果が大きい。

Imageは外部の`picsum.photos`を使うためclean buildの値に通信の揺らぎがある。ただし、画像cacheを保持した再測定でも2,373.0 msから2,635.5 msへ10.4%増加したため、通信だけでは説明できない。画像変換処理とv5 compatibility lifecycleのphase別計測を今後行う。

## Search回帰への対応

v5のHTML adapterは`pre`をraw textとして扱う。Search analyzerがその内部を再帰した結果、コードブロックのHTML markupと語彙を検索対象へ含めていた。`pre`、`script`、`style`を検索本文から除外し、コードブロックがword tableに入らない回帰テストを追加した。

この修正前のbranch固有docs出力はv4.0.8の1,232,333 bytesに対しv5が1,958,716 bytesだった。修正後の同一ソース比較では前述のとおり実質同等になった。

## 制約

- 数値は単一マシンのwall-clock timeであり、CPU、温度、バックグラウンド処理を専有していない。
- Node.jsがRosetta経由のx64実行だったため、arm64 native環境では絶対値が変わり得る。
- 5回または3回の中央値であり、統計的な性能保証ではない。
- devは1ページの初回と直後の再取得だけを測定した。HMR、複数ページ巡回、ファイル変更後の再生成は別途測定が必要である。
- Imageだけは外部サービスへの依存を含む。再現性の高い追跡にはfixture画像をローカルHTTP serverから配信する必要がある。
