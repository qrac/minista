# minista v5設計レビュー

確認日: 2026-09-05

対象: `8ef4949db7ec26c37d4af644585a556156b9f9e1`。この文書はレビューと提案であり、実装済みのCurrentや採用済みADRを変更するものではありません。

## 判断

Core / Feature / Adapterの方向性は維持する価値があります。特にrenderer port、安全な公開manifest、structured diagnostics、SSGへのMDX・render asset統合は、互換性と内部の自由度を両立しています。

次の改善で最も効果があるのは、既存の抽象化が実行全体を管理するようにすることです。現在はfeature単位のdomain処理をCoreへ移していますが、feature間の実行順と成果物の確定はVite hookや個別adapterへ分散しています。ここが設計上の宣言と実装の主な差です。

大規模な公開API変更やpackage分割より、出力transactionの修正、config互換性の明確化、application単位の実行計画を優先することを推奨します。

## 1. 出力transactionはViteの保持設定を尊重する必要がある

優先度: P1。実buildで再現。

`build.emptyOutDir: false`のprojectで、事前に`dist/keep.txt`を置いてbuildすると、成功後に消えます。

`ViteOutputTransaction.begin()`はoutDir全体をbackupへrenameし、clientは空の場所にbuildします。commitでbackupを削除するため、Viteが既存ファイルを保持する設定でも実質的に全置換されます。外部ツールとoutDirを共有するprojectに影響します。

参照: [output-transaction.js](../../packages/minista/src/adapters/vite/output-transaction.js)、[app-builder.js](../../packages/minista/src/adapters/vite/app-builder.js)。

改善案:

- transactionへ解決済みの出力保持方針を渡す。保持モードは既存ファイルを含む作業領域へbuildし、cleanモードと区別する。
- root自身だけでなくrootの祖先をoutDirに指定した場合も、transaction開始前に拒否する。
- 最終的に実際に書き込む出力先とtransaction対象が一致することを確認する。
- 正常終了、client失敗、metadata失敗、保持モードの既存ファイルを同じ出力contractで検証する。

現在の「build失敗時に前の出力を戻す」方針は有用です。修正対象はその実現方法です。

## 2. plugin名の一致ではlegacy configの互換性を判定できない

優先度: P1。実buildで再現。

`isSsrBuild`で同名pluginのオプションを変えるconfigを用意しました。SSR用transformは`render-options`、client用transformは`client-options`をpageへ埋め込むものです。

期待するHTMLは`<h1>render-options</h1>`ですが、実際は`<h1>client-options</h1>`となり、buildは成功します。

`loadViteAppConfig()`はrender/client configを評価してpluginの名前と順序だけを比較し、render側からはenvironment optionの一部しか投影しません。render用plugin instanceのclosureにある設定は引き継がれません。

参照: [app-config-loader.js](../../packages/minista/src/adapters/vite/app-config-loader.js)。Vite自身も各environment向けにconfigを再解決しており、単一Builderは単一config評価を意味しません。[Vite createBuilderの実装](https://github.com/vitejs/vite/blob/8492422b8f110625a90c702f42f30784e8cf19dc/packages/vite/src/node/build.ts#L1837)。

改善案:

- environment-awareな設定を通常経路の明示contractにする。
- legacyの`isSsrBuild`分岐を確実に扱う経路を明示する。plugin closureの同値性を名前やJSON比較で推定しない。
- 必要な場合に利用者が既存Legacy adapterを明示選択できる設計を検討する。自動判定の保証範囲も文書化する。
- 同名pluginの異なるオプションを互換性fixtureへ加える。

既存のLegacy adapterは、この問題を解決するまでは削除しない方がよいです。

## 3. domain lifecycleは全featureを対象にscheduleする

優先度: P1相当の設計課題。順序による出力差を実buildで再現。

検索対象にSVGのtext要素を挿入するページで、次の結果になりました。

| plugin順 | 最終HTMLにSVGの文字 | 検索JSONにSVGの文字 |
| --- | --- | --- |
| Search → Svg | ある | ない |
| Svg → Search | ある | ある |

各pluginは`generateBundle()`などから`processViteDocuments(..., [自分のfeature])`を呼びます。内部schedulerには当該featureと仮のinput providerしか渡らないため、sessionやDocument Storeを共有していても、feature間の順序を一括管理できません。

参照: [compatibility-lifecycle.js](../../packages/minista/src/adapters/vite/compatibility-lifecycle.js)、[Search plugin](../../packages/minista/src/plugins/search/index.js)、[Svg plugin](../../packages/minista/src/plugins/svg/index.js)。ADR-0004の「domain phaseの順序はfeature dependency graphで決める」という約束との差です。

改善案:

- `pluginXXX()`は公開option、source transform、feature登録を担当し、domain出力処理は一つのapplication coordinatorから実行する。
- 全descriptorを収集し、実行前にcapabilityと依存を検証する。外部Vite pluginのsource transform順序は通常のVite semanticsを維持する。
- domain feature生成時のdescriptorをfacadeでも再利用し、ID・requires・providesの二重記述を減らす。
- searchの入力を「最終的な可視内容を反映したdocument」と定義し、SVG・Commentなどの構造変換を終えたsnapshotへ接続する。

単に全featureを既存runnerに渡すだけでは十分ではありません。現在はSearchが`analyze`、Svgが`compose`なので、featureに`after`を追加してもphaseをまたいだ依存を表せません。既存phaseのinput/outputを整理し、document構造の確定とasset URLの反映を分ける必要があります。phase名を増やす前に、この具体的な入力contractを決めるのが先です。

受入条件は、独立したMinista pluginの順序を変えても、最終HTML・検索JSON・output ownershipが同じになることです。

## 4. Vite App Buildとの相互運用範囲を明示する

優先度: P2。hookの未実行を実buildで再現。

`ViteAppBuilderAdapter`は`builder.build(render)`と`builder.build(client)`を直接呼び、`builder.buildApp()`を呼びません。そのため、利用者のpluginにある`buildApp` hookは実行されません。追加environmentも通常経路のbuild対象になりません。

Viteでは`buildApp()`がplugin hookと`config.builder.buildApp`を呼ぶ場所です。`build(environment)`は単一environmentをbuildする別の操作です。[Viteの実装](https://github.com/vitejs/vite/blob/8492422b8f110625a90c702f42f30784e8cf19dc/packages/vite/src/node/build.ts#L1865)。

改善案:

- Ministaがrender → prepare → clientを所有することを明示したうえで、Viteのapplication hookをどこで実行するか定義する。
- `builder.buildApp()`経由へ統合する場合、userの`builder.buildApp`との二重build・順序競合を防ぐcontractを先に決める。
- 相互運用を対象外とする場合は、対象設定を黙って無視せずstructured diagnosticで知らせる。

Vite upstreamの`createBuilder()`、shared config/plugin設定には確認時点でもexperimental表記があります。Coreから隔離する現在の方針は妥当です。sharedPluginsを有効にしてこの問題を解決しようとする必要はありません。

## 5. 成功判定、診断、metadataの確定を一つの境界へ集約する

優先度: P2。戻り値の不整合はadapter単体で再現。metadataの制限は既存ADRでも認識済み。

error diagnosticを持つsessionと成功するstub builderを渡しても、App Builderは`status: "success"`を返します。また、Core runnerはhookが例外を投げた場合には停止しますが、hookがdiagnosticだけ追加した場合は後続hook・phaseを進め、最後に`ok: false`を返します。

参照: [app-builder.js](../../packages/minista/src/adapters/vite/app-builder.js)、[runner.js](../../packages/minista/src/core/lifecycle/runner.js)。この単体再現は、通常のすべてのCLI失敗が成功扱いになるという意味ではありません。

加えて、現在はoutDirをcommitした後でclaim収集・manifest・diagnosticsを書きます。後半が失敗すると新distと旧manifestが残り得ます。この制限はADR-0008/0009に明記されていますが、完成後の信頼性を高める改善対象です。

改善案:

- phase内の診断収集は許容しつつ、phase境界でerrorがあれば生成・emitへ進まない。
- claim検証とmanifest生成をcommitより前に置き、成功resultを返す前にcollectorのerror有無を確認する。
- 出力とmanifestに同じbuild generationを持たせ、read-only queryが古いmanifestを現行出力と取り違えないようにする。
- metadataの書込み失敗を含むrollback方針とcommit後のcleanup失敗の扱いを定義する。別ディレクトリの複数renameを単一のatomic transactionとは呼ばない。

## 6. Graphを軽く読み、phaseで許可する変更を限定する

優先度: P2。コード確認。性能回帰の新規計測は未実施。

`ProjectGraph.addPage()`は追加のたびに全pageを走査して重複URLを調べ、`addRoute()`も同様です。N件の登録はO(N²)になります。また`graph.snapshot()`は全Mapを複製しますが、Searchなどでは各pageの処理中にfeatureの存在確認だけのために呼ばれています。

参照: [project-graph.js](../../packages/minista/src/core/graph/project-graph.js)、[search.js](../../packages/minista/src/features/search/search.js)。Artifact Storeの`list()`もbinaryをコピーするため、画像が多いsessionで全件listを繰り返す設計は測定対象です。

改善案:

- URL → PageId、pattern → RouteIdのindexをGraph内部に持つ。
- `hasFeature()`、`getPage()`、ownerやscopeで絞るArtifact queryを提供し、軽い読取りのための全体snapshotを避ける。
- 外部公開snapshotを保ちつつ、内部はphase中に有効なread viewを使う。
- `PhaseContext`は現在どのphaseにも同じ可変Graph・Emitterを渡す。まずemit前の出力禁止とfinalizeでのroute変更禁止など、重要な不変条件を小さなguardと型で保証する。

devの影響routeだけを再解決する方針は維持します。次の性能測定は1ページ追加・削除・共通layout変更と、1,000/10,000ページでのgraph構築時間・peak memoryを対象にすると、改善効果を評価できます。

## 7. 設計上の保証をrelease gateにする

優先度: P2。

`vite.md`は最低・推奨・latest minorのintegration testを掲げていますが、確認した`.github/workflows`にはdocs deployのみで、PRのtest/typecheckやversion matrixはありません。今回の成功はVite 8.2.1環境についての結果です。`peerDependencies.vite: ^8.0.0`の全範囲の保証にはなりません。

最低versionを楽観的に許容する方針は、experimental APIを使うadapterには不向きです。最低versionでcontract testを通してからrangeを決める方が、fallback追加や利用者側の調査を減らせます。

gateには通常の成功fixtureに加えて、次を含めることを推奨します。

- Minista pluginの順序入替えと最終出力の一致。
- 同名pluginのSSR/client別option。
- 出力保持、client失敗、metadata失敗と前回出力の整合性。
- 公開manifestにprops・source・絶対pathを含めない既存検証。
- Vite最低・基準・最新の対応versionと、React 18/19・Preactの代表fixture。

文書も実装と合わせる必要があります。例えば`vite.md`のReact欄には同期`renderToString()`が現在の実装とありますが、実装とarchitectureではReact 19にstatic rendererを選択済みです。roadmapの「全Stage完了」と、今回確認したlifecycleの残る境界も整合させるべきです。

## 推奨する進め方

1. 出力保持と同名pluginのconfig誤適用を先に修正し、今回の再現ケースを回帰testにする。
2. application coordinatorを一つ設け、全featureのdescriptor、documentの段階、Vite App Buildの対応範囲を整理する。公開`pluginXXX()`は維持する。
3. 成功判定とmetadata確定を整理し、Graphの軽量query・indexとphase guardを導入する。
4. 対応version matrixと大規模fixtureで保証を固定し、その実装に合わせてADR・Current・roadmapを更新する。

Coreの別package化、独自bundler、Bundled Devのdefault化、MCP、新しい公開feature APIは、今回の問題を解消する前提ではありません。現在ある境界を完成させることで、後の機能追加を少ない変更で行える設計にできます。
